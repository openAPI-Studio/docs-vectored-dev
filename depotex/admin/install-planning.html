Plan an installation

Components, requirements, sizing, network and storage to decide before installing Depotex

Depotex is two programs, the server (API, package-manager endpoints, background jobs) and the web app, in front of PostgreSQL, optional Redis and artifact storage. Decide these before installing: they're the parts that are hard to change later.

Every feature behaves the same either way. Start with one server if you're unsure: going to a cluster later means adding Redis and shared storage, not reinstalling.

3. PostgreSQL

  • A supported PostgreSQL release, 15 or later (the Helm chart's built-in database is 17; the server image's backup tools are 18 and work with 18 and older). Managed services (Amazon RDS and Aurora PostgreSQL, Google Cloud SQL, Azure Database for PostgreSQL) work.
  • One database for Depotex, owned by the role Depotex connects as. The role needs CREATEROLE if plugins use databases, and must not be a superuser.
  • Connections: each server opens up to pool_max_conns (default 4, or the number of CPUs if more). Keep servers × pool_max_conns plus room for maintenance under max_connections. See Database connections.
  • Use TLS (sslmode=verify-full) when the database isn't on the same host, and back the database up with your platform's tools as well as with Depotex backups.

4. Storage

  • Size it for your artifacts plus growth: proxies keep copies of everything fetched, Docker images are large. Cleanup policies and quotas keep it in check (see Spaces).
  • Object storage (S3, MinIO, Azure) is the usual choice and the only one that needs nothing extra for a cluster. On AWS the server can use its IAM role instead of keys.
  • Each server also has a small data folder of its own (/app/data in the image): the encrypted bootstrap file, its search index (rebuilt when missing) and its log files. Give it persistent disk, about 10 GiB to start; the search index grows with the number of versions.
  • Backups and scans need temporary space: a compressed database dump for backups (BACKUP_TEMP_DIR), the largest unpacked image for image scans (IMAGE_SCAN_TMP_DIR).

5. Sizing

Starting points, to be adjusted from what monitoring and the system check show under your load:

Company-wide, high availability3+ × 4 CPU, 8 GiB2–3 × 1 CPU, 1 GiB8+ CPU, 32 GiB, replicatedreplicated, 1 GiB
  • Most load is package-manager traffic from CI: count builds per hour and dependencies per build, not people.
  • Small files are database-bound: a faster database (and pool_max_conns to match) helps more than more servers. Large files are network- and storage-bound.
  • Image scans (Syft) and SBOM inspection run one at a time per cluster in the background; they use CPU and temporary disk on the server that runs them.

Outbound from the server, only for what you use: upstream registries for proxy repositories, identity providers (single sign-on, Entra ID, Google), SMTP or Amazon SES, webhook targets, OSV vulnerability data (or upload it offline in Settings → Vulnerability data; C/C++ advisories for Conan packages come from OSV's data files at osv-vulnerabilities.storage.googleapis.com or your copy of it, whichever source is chosen), and plugins' declared hosts. An outbound HTTP proxy and private certificate authorities are set in Settings → Repositories. Nothing is sent to Vectored, apart from the installation ID when the vibe artifacts package list is downloaded.

7. Address and TLS

  • Give Depotex its own host name (https://depotex.example.com); it can't be served under a path.
  • Terminate TLS at your proxy or ingress. Package managers and single sign-on require HTTPS in practice.
  • Set TRUSTED_PROXIES (backend.trustedProxies in Helm) to the proxies in front, or every request seems to come from the proxy.
  • Allow large request bodies and long timeouts at the proxy for big uploads and downloads.

8. Before you install

  • PostgreSQL database and role created; Redis ready if you run a cluster; bucket or container created.
  • DNS name and TLS certificate.
  • A place to keep secrets: CONFIG_ENCRYPTION_KEY, the first administrator's password, the setup and recovery keys.
  • Who will request the license, and with which tier, user and server counts (see Licensing).
  • Email (SMTP or Amazon SES) for invitations and password resets.
  • Your identity source: local accounts, LDAP or Active Directory, Entra ID, Google Workspace, SCIM, and single sign-on.
