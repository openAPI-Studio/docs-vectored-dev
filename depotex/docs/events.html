Events Reference

The events Depotex raises, for policies, automation and plugins

Depotex raises an event for each important operation. Policies, automation and plugins react to these events: a policy can stop an operation before it happens, and automation or a plugin can act after it has happened.

1. Before and after

PhaseWhenWhat subscribers can do
BeforeBefore the operation runsStop it with a message (on events marked *blocking*), or adjust the few fields the event allows. They have a few seconds at most.
AfterOnce the operation has succeededReact to it: send an alert, notify another system. They can't undo or slow down the operation.

Passwords, keys and similar secrets are never included in an event.

2. Delivery

  • After-events are saved in the database together with the change that caused them, so they are never lost when a server restarts, and each is delivered once across all servers of a cluster.
  • They usually arrive within a few seconds.
  • A subscriber that fails is retried with increasing delays (up to 8 times by default, over several hours); after that the delivery is marked as failed and kept for 30 days.
  • The same event can occasionally be delivered twice (for example after a server restart mid-delivery). Plugins and integrations must handle repeats.

Events marked policies accept organization policies.

5. Failed deliveries

Settings → Advanced → Event deliveries (super admins) lists events that couldn't be delivered to a subscriber after every retry, with the last error. Retry once the problem is fixed, or Discard it. Failed deliveries are kept for 30 days (EVENT_DEAD_RETENTION_DAYS).

6. Performance

  • An event nobody listens to costs nothing measurable.
  • Before-subscribers (policies, plugins) run while the user waits: each adds to the time the action takes, up to the time limit below. Keep them simple.
  • Once something listens to an after-event, every occurrence writes to the database and is delivered in the background. On frequent events such as auth.login or busy scheduled jobs, many subscribers or slow ones add database load and delivery backlog. Subscribe only to the events you need.
  • Using an API token is deliberately not an event: a check on every request would slow down all API traffic. Use token settings and the organization's token rules instead.

On a busy installation, a slow or failing after-subscriber on a frequent event (for example every sign-in) builds up retries in the database. Watch the delivery settings below and keep such subscribers fast.
