Events Reference

Every event the Wiki raises, for policies, automation and plugins: pages, spaces, Q&A, calendars and the platform

The Wiki raises an event for each important operation: a page published, a comment added, a question asked, a space imported, a user created. Policies, automation and plugins react to these events: a policy or plugin can stop an operation before it happens, and automation or a plugin can act after it has happened.

1. Before and after

PhaseWhenWhat subscribers can do
BeforeBefore the operation runsStop it with a message (on events marked *blocking*), or adjust the few fields the event allows. They have a few seconds at most.
AfterOnce the operation has succeededReact to it: send an alert, notify another system. They can't undo or slow down the operation.

Passwords, keys and similar secrets are never included in an event. Some events leave out who acted: a vote (qna.vote) doesn't say who voted.

2. Delivery

  • After-events are saved in the database together with the change that caused them, so they are never lost when a server restarts, and each is delivered once across all servers of a cluster.
  • They usually arrive within a few seconds.
  • A subscriber that fails is retried with increasing delays (up to 8 times by default, over several hours); after that the delivery is marked as failed and kept for 30 days. Administrators see deliveries under Settings → Advanced → Event deliveries (events:admin).
  • The same event can occasionally be delivered twice (for example after a server restart mid-delivery). Plugins and integrations must handle repeats.

A change made through Kee or an outside AI app raises the same page, comment and label events as a change made by hand, as the person, with a via field: kee for a change applied from Ask Kee, mcp for one an outside AI app wrote. Reading through an app raises no event.

In the tables, yes · policies marks events that also accept organization policies; plain yes events accept only platform policies and plugins. Events marked no can't be stopped.

24. Using events

  • Stop something: write a policy on a blocking event's before phase, for example require a review before page.publish, or refuse space.import.start outside some spaces.
  • Be told or tell another system: write an automation rule on the after phase, for example post every qna.question.create to a chat channel with a webhook.
  • Anything else: a plugin can receive both phases with its own logic.
