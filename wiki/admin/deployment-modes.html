Single server & cluster

Run the Wiki on one server or many with the same features

Every feature of the Wiki works the same on one server or many. What changes is how the servers coordinate.

1. What a cluster shares

  • Pages and edits are saved in PostgreSQL first, then announced to the other servers, so two people editing the same page on different servers see each other's changes.
  • Background work (imports, analytics rollups, scheduled publishing, review-by reminders, Q&A reputation) runs once per cluster, whichever server picks it up.
  • Settings, such as anonymous access, search engines and video sites, apply on every server within seconds of being saved.
  • Files go to the shared storage, so any server serves any image or video.

2. Redis

Give Redis as a URL in the setup wizard, the unattended setup file (cache.redis_url), on a running installation in Settings → Clustering → Redis (see Add Redis to a running installation), or on the recovery page when a server can't start:

KindURL
One serverredis://:password@redis.internal:6379/0, or rediss:// for TLS
Sentinel groupredis+sentinel://:password@s1:26379?master_name=mymaster&addr=s2:26379&addr=s3:26379
Redis Clusterredis+cluster://:password@n1:6379?addr=n2:6379&addr=n3:6379
  • Each kind takes TLS (rediss, rediss+sentinel, rediss+cluster), a private certificate authority (ca_file=/path/ca.pem) and Redis ACL users (user:password@).
  • Redis coordinates; PostgreSQL keeps the records. If Redis becomes unavailable, the Wiki keeps working: sign-in and sessions (kept in PostgreSQL), scheduled jobs once per cluster, and live updates through PostgreSQL. Rate limits are then counted by each server on its own. It logs one warning when Redis goes and one message when it returns.
  • A failover can lose the last few writes to Redis; results stay correct because PostgreSQL holds the records.

3. Add Redis to a running installation

An installation set up without Redis runs on one server. To grow it into a cluster, add Redis first. Super admins do it on Settings → Clustering, in the Redis card:

  1. Open Settings → Clustering — The Redis card says Not set up and lists the servers that are running, each with No Redis.
  2. Select Set up Redis — Enter the Redis URL (one server, Sentinel or Redis Cluster, as in the table above). Put the password in the URL or in Password.
  3. Select Test connection — The Wiki connects to every server the URL names. It says Connected, or why not: the URL can't be used, Redis refused the user name or password, or Redis can't be reached from this server. Nothing is saved yet.
  4. Select Save — The URL is tested again and saved, encrypted, with the rest of the setup configuration.
  5. Restart the server — A server starts using Redis when it restarts. Until then the card marks it Restart needed; after the restart it shows Uses Redis.
  6. Start the next server — Once every running server shows Uses Redis, start the second server with the same database and shared storage. A server can't join while another one runs without Redis: it stops with an error that says what to do.
  • Change works the same way. The saved password is never shown: the form shows the URL without it, and leaving Password empty keeps it. Each server shows Restart needed until it restarts with the new setting.
  • Changing to a different Redis while several servers run splits the cluster until every server has restarted: live updates and rate limits aren't shared between restarted servers and the others for that time. Restart them one after another without a pause, or change Redis while one server runs.
  • Remove forgets the URL, so the server runs without Redis after its next restart. It is only offered while one server runs: a cluster needs Redis.
  • Each change raises cluster.redis.update (see Events) and is in the audit log as redis:update, redis:remove and redis:test. Only super admins have the redis:admin permission this needs.

4. Database connections

Each server opens up to pool_max_conns connections to PostgreSQL (by default 4, or the number of CPUs if that is more). Set it in DATABASE_URL, for example postgres://wiki:…@db:5432/wiki?pool_max_conns=25, at a server's first start. In a cluster every server opens its own, so keep servers × pool_max_conns, plus room for maintenance, under PostgreSQL's max_connections.

5. Read cache

Each server keeps what most requests look up, such as roles and settings, in its own memory. PostgreSQL tells every server the moment one of these changes, and each server also checks every second, so a change applies everywhere almost at once, with or without Redis. READ_CACHE_ENABLED=false turns it off on one server (see Environment variables).

6. Clustering page

Settings → Clustering (super admins) lists every server: its status, health, name and machine ID, version, CPU, memory, uptime and last heartbeat, and the leader. A server that stops responding gets a notice above the table.

StatusMeaning
activeRunning.
drainingShutting down: finishing its work before it stops.
leftShut down cleanly. Removed from the list after a day (CLUSTER_DEAD_NODE_TTL).
deadStopped sending heartbeats without shutting down cleanly. It becomes active again by itself with its next heartbeat; one that stays dead is removed after a day.
